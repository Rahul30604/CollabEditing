3.4 Authentication Flow
--------------------------------------------------------------------------------

Registration:
1. User sends POST /api/auth/register with {name, email, password}
2. Validate input (email format, password min 6 chars)
3. Check email uniqueness
4. Hash password with BCrypt
5. Save user to database
6. Generate JWT access token (24h) and refresh token (7d)
7. Return tokens + user info

Login:
1. User sends POST /api/auth/login with {email, password}
2. Spring Security AuthenticationManager authenticates
3. If valid, generate JWT tokens
4. Return tokens + user info

Protected Requests:
1. Client sends Authorization: Bearer <token>
2. JwtAuthenticationFilter extracts token
3. Validates signature and expiry
4. Loads user by ID from token subject
5. Sets SecurityContext authentication
6. Request proceeds to controller

3.5 API Endpoints
--------------------------------------------------------------------------------

AUTH:
  POST /api/auth/register      Public   Register new user
  POST /api/auth/login         Public   Login
  GET  /api/auth/me            Auth     Get current user profile

DOCUMENTS:
  POST   /api/documents        Auth     Create document
  GET    /api/documents        Auth     List accessible documents
  GET    /api/documents/{id}   Auth     Get single document
  PUT    /api/documents/{id}   Auth     Update document (OWNER/EDITOR only)
  DELETE /api/documents/{id}   Auth     Delete document (OWNER only)

SHARING:
  POST   /api/documents/{id}/share          Auth/Owner   Share with user
  GET    /api/documents/{id}/share          Auth/Owner   List permissions
  DELETE /api/documents/{id}/share/{userId} Auth/Owner   Remove permission

3.6 Security Configuration
--------------------------------------------------------------------------------
- Stateless sessions (no server-side session)
- CORS enabled for http://localhost:3000
- /api/auth/** endpoints are public
- All other endpoints require authentication
- BCrypt password encoding
- JWT signed with HMAC-SHA256 (Base64 encoded secret)

3.7 Permission Logic
--------------------------------------------------------------------------------

Document Access:
- User can see documents they own OR have a permission entry for
- DocumentRepository.findAccessibleByUserId() handles this query

Document Edit:
- OWNER and EDITOR can update title/content
- VIEWER gets 403 (permission denied)

Document Delete:
- Only OWNER can delete
- Deleting removes all associated permissions first

Document Share:
- Only OWNER can share
- Cannot share with yourself
- Cannot assign OWNER role (only EDITOR/VIEWER)
- If permission exists, role is updated (upsert behavior)

3. KEY-BASED EDITING CONTROL
================================================================================

3.1 Concept
--------------------------------------------------------------------------------
Only one user can actively edit a document at a time. This eliminates
write conflicts while maintaining real-time collaboration (viewers see
changes live).

3.2 Workflow
--------------------------------------------------------------------------------

    User A requests key
           |
           v
    Server checks: is key free?
           |
       YES |          NO
           v           v
    Key assigned    Added to queue
    to User A      (position returned)
           |
           v
    User A edits (others are read-only)
           |
           v
    User A releases key (or disconnects)
           |
           v
    Next user in queue gets key
           |
           v
    WebSocket broadcast: new key holder

3.3 Backend Implementation
--------------------------------------------------------------------------------
- EditingKeyManager (in-memory, thread-safe)
  - ConcurrentHashMap<documentId, userId> for key holders
  - ConcurrentLinkedQueue<userId> per document for waiting
  - synchronized methods for request/release/forceRelease
  - removeUser() cleans up all docs on disconnect

- EditingKeyController
  - POST /api/documents/{id}/key/request  -> acquire or queue
  - POST /api/documents/{id}/key/release  -> release, assign next
  - GET  /api/documents/{id}/key/status   -> who holds it

- WebSocket broadcast on /topic/document/{id}/key for status changes

3.4 Frontend Implementation
--------------------------------------------------------------------------------
- "Request Key" button when key is free or user is queued
- Green "Editing" chip when user holds the key (with release action)
- Orange "Locked by X" chip when someone else holds it
- Queue position indicator
- Document textarea disabled when user doesn't hold key
- Key auto-released on disconnect (backend WebSocketEventListener)

================================================================================
4. WEBSOCKET REAL-TIME COLLABORATION
================================================================================

4.1 STOMP Destinations
--------------------------------------------------------------------------------

Client sends to (via /app prefix):
  /app/document/{id}/edit      Content changes (key holder only)
  /app/document/{id}/cursor    Cursor position updates (any user)
  /app/document/{id}/presence  Join/leave notifications

Server broadcasts to (via /topic prefix):
  /topic/document/{id}/edits      Incoming content from key holder
  /topic/document/{id}/cursors    Other users' cursor positions
  /topic/document/{id}/presence   User join/leave events
  /topic/document/{id}/key        Key holder changes
  /topic/document/{id}/events     RabbitMQ forwarded events (saves, etc.)
  /topic/notifications            Global notification events

4.2 Authentication
--------------------------------------------------------------------------------
- WebSocketAuthInterceptor intercepts STOMP CONNECT frame
- Extracts Bearer token from native "Authorization" header
- Validates JWT and sets UsernamePasswordAuthenticationToken as Principal
- All @MessageMapping methods have access to Principal for user identification

4.3 Message Types
--------------------------------------------------------------------------------
- DocumentEditMessage: documentId, userId, userName, content, title, timestamp
- CursorMessage: documentId, userId, userName, position, selectionStart, selectionEnd
- PresenceMessage: documentId, userId, userName, action (JOINED/LEFT)

4.4 Disconnect Handling
--------------------------------------------------------------------------------
- WebSocketEventListener listens for SessionDisconnectEvent
- On disconnect: releases any editing keys held by the user
- Reassigns key to next in queue if applicable
- Broadcasts key status change to all subscribers

4.5 Frontend WebSocket Service
--------------------------------------------------------------------------------
- Singleton STOMP client (websocketService.js)
- SockJS transport with auto-reconnect (5 second delay)
- JWT token sent on CONNECT
- Helper methods: subscribeToEdits, subscribeToCursors, subscribeToPresence,
  subscribeToKeyChanges, sendEdit, sendCursor, sendPresence
- Cleanup: unsubscribeFromDocument on component unmount

5. RABBITMQ EVENT ARCHITECTURE
================================================================================

5.1 Configuration
--------------------------------------------------------------------------------
- Exchange: collabeditor.exchange (Topic type)
- Queues:
  - document-updates (bound to "document.*")
  - notifications (bound to "notification.*")
- Message format: JSON via Jackson2JsonMessageConverter
- Routing keys:
  - document.saved
  - document.updated
  - notification.send

5.2 Event Flow
--------------------------------------------------------------------------------

    User saves document
           |
           v
    DocumentService.updateDocument()
           |
    +------+------+
    |             |
    v             v
  Save to DB   EventPublisher.publishDocumentSaved()
                      |
                      v
                RabbitMQ Exchange
                      |
              +-------+-------+
              |               |
              v               v
    document-updates    notifications
       queue              queue
              |               |
              v               v
    EventConsumer       EventConsumer
    (handleDocUpdate)   (handleNotification)
              |               |
              v               v
    WebSocket broadcast  WebSocket broadcast
    /topic/document/X/   /topic/notifications
         events

5.3 Benefits
--------------------------------------------------------------------------------
- Decouples save operation from notification delivery
- User doesn't wait for notifications to complete
- Scalable: can add more consumers (embedding worker in Phase 3)
- Reliable: messages persist in queue if consumer is down

6. VERSION HISTORY
================================================================================

6.1 Database Schema
--------------------------------------------------------------------------------

TABLE: document_versions
- id (BIGINT, PK, AUTO_INCREMENT)
- document_id (BIGINT, FK -> documents.id)
- version (INT, NOT NULL)
- title (VARCHAR, NOT NULL)
- content (LONGTEXT)
- modified_by (BIGINT, FK -> users.id)
- created_at (DATETIME)

6.2 When Versions Are Created
--------------------------------------------------------------------------------
- Every time a user saves a document (PUT /api/documents/{id})
- A new version number is auto-incremented (MAX + 1)
- The snapshot captures the document's content at that point in time

6.3 API Endpoints
--------------------------------------------------------------------------------
  GET    /api/documents/{id}/versions           List all versions (no content)
  GET    /api/documents/{id}/versions/{v}       Get specific version with content
  POST   /api/documents/{id}/versions/{v}/restore   Restore document to version
  GET    /api/documents/{id}/versions/compare?versionA=X&versionB=Y   Side-by-side

6.4 Restore Behavior
--------------------------------------------------------------------------------
- Only the document OWNER can restore
- Restoring updates the document's current content to the version's content
- A NEW version is created marking the restore (so history is preserved)
- The document is never actually "rolled back" — it always moves forward

6.5 Frontend Version History Page
--------------------------------------------------------------------------------
- Route: /documents/:id/history
- Lists all versions in descending order (newest first)
- Per version: version chip, title, modified by, timestamp
- Actions:
  - View: opens dialog showing full content of that version
  - Compare: select two versions for side-by-side comparison
  - Restore: confirmation dialog, creates new version

================================================================================
4. EMBEDDING PIPELINE
================================================================================

4.1 Chunking Strategy
--------------------------------------------------------------------------------
- Splits document content by whitespace into words
- Chunk size: 500 words
- Overlap: 100 words between consecutive chunks
- Each chunk gets a unique ID: {documentId}_chunk_{index}

Example for a 1200-word document:
  Chunk 0: words 0-499
  Chunk 1: words 400-899
  Chunk 2: words 800-1199

4.2 Embedding Generation
--------------------------------------------------------------------------------
- Uses OpenAI text-embedding-3-small model
- Batch processing (20 texts per API call)
- Generates 1536-dimensional vectors per chunk

4.3 ChromaDB Storage
--------------------------------------------------------------------------------
- Collection: collabeditor-documents
- Per chunk stored:
  - id: "{documentId}_chunk_{index}"
  - embedding: float[1536]
  - document: chunk text content
  - metadata: { document_id, chunk_index, title }
- On re-index: delete all old chunks for document, then upsert new ones
- Supports filtered queries (by document_id)

4.4 Async Flow via RabbitMQ
--------------------------------------------------------------------------------
- Queue: embedding-generation
- Routing key: embedding.generate
- Trigger: every document save (PUT /api/documents/{id})
- Consumer: EmbeddingConsumer
- Error handling: logs error, acks message (no DLQ yet)
- User experience: save returns immediately, embeddings process in background

================================================================================
5. RAG (RETRIEVAL-AUGMENTED GENERATION)
================================================================================

5.1 Document Q&A Flow
--------------------------------------------------------------------------------
1. User submits question via POST /api/documents/{id}/ask
2. Question is embedded using text-embedding-3-small
3. ChromaDB queried with embedding, filtered to document_id
4. Top 5 most similar chunks retrieved
5. Context built from chunk texts (joined with separators)
6. System prompt constructed with document context
7. OpenAI GPT-4.1 called with system prompt + user question
8. Response returned with answer + source snippets

System Prompt Template:
  "You are an AI assistant helping users understand a document.
   Answer questions based ONLY on the provided document context below.
   If the answer cannot be found in the context, say so clearly.
   DOCUMENT CONTEXT: {chunks}"

5.2 Summarization Flow
--------------------------------------------------------------------------------
1. User requests summary via POST /api/documents/{id}/summary
2. A general embedding is created for "summarize this document"
3. Top 20 chunks retrieved (more content for comprehensive summary)
4. All chunk texts concatenated
5. Summarization prompt sent to GPT-4.1
6. Structured summary returned (overview + key points + details)

5.3 Semantic Search Flow
--------------------------------------------------------------------------------
1. User submits query via POST /api/search
2. Query embedded using text-embedding-3-small
3. ChromaDB queried across ALL documents (no filter)
4. Top 10 results retrieved
5. Results filtered to only accessible documents (permission check)
6. Returns: documentId, title, snippet, relevanceScore (1 - distance)

  - restore(docId, v) -> POST /documents/{id}/versions/{v}/restore
  - compare(docId, vA, vB) -> GET /documents/{id}/versions/compare

aiService.js:
  - askQuestion(docId, question) -> POST /documents/{id}/ask
  - summarize(docId) -> POST /documents/{id}/summary
  - search(query) -> POST /search

================================================================================
7. WEBSOCKET SERVICE
================================================================================

7.1 websocketService.js (Singleton)
--------------------------------------------------------------------------------
  Transport: STOMP over SockJS
  Endpoint: http://localhost:8080/ws
  Auth: JWT token in CONNECT frame Authorization header
  Reconnect: 5-second delay, automatic
  Heartbeat: 10s incoming, 10s outgoing

7.2 Methods
--------------------------------------------------------------------------------

Connection:
  - connect(token): activates STOMP client
  - disconnect(): deactivates, unsubscribes all
  - onConnect(callback): fires when connected (or immediately if already)

Subscriptions:
  - subscribeToEdits(docId, callback)      /topic/document/{id}/edits
  - subscribeToCursors(docId, callback)    /topic/document/{id}/cursors
  - subscribeToPresence(docId, callback)   /topic/document/{id}/presence
  - subscribeToKeyChanges(docId, callback) /topic/document/{id}/key
  - subscribeToEvents(docId, callback)     /topic/document/{id}/events

Publishing:
  - sendEdit(docId, content, title)        /app/document/{id}/edit
  - sendCursor(docId, pos, selStart, selEnd) /app/document/{id}/cursor
  - sendPresence(docId, action)            /app/document/{id}/presence

Cleanup:
  - unsubscribeFromDocument(docId): removes all subscriptions for a doc

7.3 Usage in Editor
--------------------------------------------------------------------------------
On mount:
  1. Connect WebSocket with token
  2. Subscribe to edits, key changes, presence
  3. Send JOINED presence message

On remote edit received:
  - Update content/title in state (if from different user)

On save:
  - Call documentService.update()
  - Send edit via WebSocket to broadcast

On unmount:
  - Send LEFT presence message
  - Unsubscribe from document topics
